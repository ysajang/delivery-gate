# 납품 전 보안 게이트

마스터는 배운 적 없는 스택(C# PHP TypeScript Nginx Next.js)으로 AI를 써서 납품한다.
코드를 읽어서 결함을 잡는 경로가 막혀 있으므로 방어는 기억하는 체크리스트가 아니라
**통과 못 하면 막히는 자동 게이트**여야 한다. 이 스킬은 그 절차다.

## 적용 대상

적용한다: 고객 손에 넘어가는 코드, 고객 데이터가 지나가는 코드, 고객 명의 인프라에 올라갈 것
적용하지 않는다: 마스터 개인용 도구, "데모용"이라고 명시된 것
애매하면 적용한다.

## 절차

### 1. 게이트 실행

```bash
cd ~/gate && ./gate.sh ~/projects_wsl/<프로젝트명>
```

프로젝트는 `~/projects_wsl` 아래에 있다. 이 경로를 임의로 바꾸지 말 것.
게이트가 없거나 오래됐으면 먼저 `cd ~/gate && git pull && ./install.sh`.

리포트는 `~/gate/reports/<프로젝트>-<타임스탬프>/`에 남는다.
**리포트를 고객에게 보내거나 커밋하지 말 것** -> 취약점 위치가 그대로 적혀 있다.

### 2. 결과 판정

| 표시 | 의미 | 행동 |
|---|---|---|
| FAIL | 차단 | 해결 전에는 납품하지 않는다 |
| WARN | 차단 아님 | 무시하지 않고 인수인계 문서에 기록한다 |
| SKIP | 미실행 | 왜 안 돌았는지 확인한다. 통과가 아니다 |

FAIL 상세는 `reports/.../` 안의 JSON을 읽어 판정한다.

- `secrets-*.json` -> 시크릿. 커밋 이력에 있으면 파일 삭제만으로는 안 지워진다
- `sast.json` -> semgrep ERROR 지적. 규칙 이름과 파일·줄 번호를 그대로 보고한다
- `dep-npm-prod.json` -> 프로덕션 취약점 중 수정 가능한 것

주의할 함정 두 가지

1. **G2 PASS는 안전하다는 뜻이 아니다.** semgrep은 인가 결함(IDOR)을 원리상 잡지 못한다.
   API 라우트 30개짜리 ERP에서 지적 0으로 나온 실측이 있다. PASS를 안전으로 보고하지 말 것
2. **WARN 파싱 실패**는 그 파일에 룰이 안 돌았다는 뜻이다. 커버리지 구멍이므로 수동 확인 대상에 올린다

### 3. 수동 확인

자동 게이트를 통과해도 `~/gate/manual-checks.md`를 수행한다. 인가·IDOR·비즈니스
로직은 앱마다 정답이 달라 룰로 표현되지 않는다. 실제로 터지는 것은 이쪽이다.

우선순위는 이 순서다: 인가·IDOR > 하드코딩 시크릿 > DB 권한 > 노출면 > 비즈니스 로직.

### 4. 인수인계 문서에 기록

마스터는 인프라를 고객 명의로 넘기는 방침이다. 이관 후 터진 것의 책임 경계가
문서에 없으면 분쟁에서 불리하다. 다음을 적는다.

- 점검한 범위 (게이트 3단 + 수동 확인 항목)
- 점검하지 않은 범위
- 수정본이 없어 남긴 취약점 목록 (게이트가 WARN으로 표시한 것)
- 이관 시점 이후의 책임 경계

## 하지 말 것

- FAIL을 우회하고 납품하지 않는다. `--no-verify` 류의 우회를 지름길로 쓰지 않는다
- 게이트 통과를 "보안 점검 완료"로 고객에게 표현하지 않는다. 잡은 범위만 말한다
- 리포트 JSON을 고객에게 그대로 보내지 않는다
- 스캔 결과를 근거로 종결된 고객에게 먼저 연락하지 않는다. 연락 여부는 마스터가 판단한다

## 게이트가 잡는 것과 못 잡는 것

잡는다: 커밋된 시크릿, 명백한 인젝션·XSS 패턴, 컨테이너 root 실행, 취약 의존성
못 잡는다: 인가 결함, IDOR, 비즈니스 로직, 권한 우회, 데이터 유출 경로

못 잡는 쪽이 실제 사고의 주력이다. 게이트는 바닥을 깔 뿐이고 그 위는 수동이다.
